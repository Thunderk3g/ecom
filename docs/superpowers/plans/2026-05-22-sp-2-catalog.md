# SP-2: Catalog — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the catalog domain on top of the SP-1 foundation — categories (tree), products, variants, attributes, bundles, images, and full-text search (Postgres FTS + pg_trgm). Expose a storefront read API and an admin CRUD API. Every tenant table gets RLS. No image processing yet (SP-8) and no inventory (SP-3) — variants are referenced by SP-3 via FK.

**Architecture:** Drizzle schemas extend the existing `src/db/schema/` set. Migrations continue numerically from SP-1's 0004 (next number is 0005). Module services in `src/modules/catalog/` are pure functions over `withTenant()` — same pattern SP-1 established. Storefront endpoints live under `src/app/api/v1/catalog/`, admin endpoints under `src/app/api/v1/admin/catalog/`. Search uses Postgres `tsvector` columns + GIN indexes + pg_trgm; no external search engine.

**Tech Stack additions:** none beyond SP-1. Drizzle adds `pgEnum`, `tsvector`, `jsonb`, GIN/btree indexes. zod schemas for request bodies.

## Assumptions (locked unless overruled)

1. **Category tree model:** **adjacency list** (`parent_id` FK to `categories.id`). Reason: shallow stationery taxonomy (depth 3–4 typical), no need for nested-set complexity. Reading a subtree uses a recursive CTE — fine at this scale. Reversible to materialized path or nested-set if read patterns shift; the API surface (`GET /categories` returns a tree) hides the storage shape.
2. **SKU uniqueness:** unique within `(store_id, sku)`, not globally. Different stores can use the same SKU.
3. **Variant axes:** stored as `jsonb` (`{size: "A5", color: "blue", pack: 5}`) per spec §5.2 — no normalized `variant_axis_values` table for v1. GIN index on `product_variants.axes` powers facet queries.
4. **Attribute storage:** two-tier — `attribute_definitions` registers the schema (store-scoped), `products.attributes` is freeform `jsonb` validated against the registry at write time by the module service (zod-generated from the registry row).
5. **Search:** Postgres `tsvector` column `products.search_tsv` generated by trigger from name + description + brand + attribute values; weighted (A: name, B: brand, C: description, D: attributes). Combined with `pg_trgm` similarity on `name` for typo tolerance. No separate `search_index` table — denormalized into `products`.
6. **Bundles:** modeled as `products.type = 'bundle'` plus `bundle_components(bundle_variant_id, component_variant_id, qty)`. Bundle price is set on the bundle variant; inventory decrement of components is SP-3's concern (SP-2 just exposes the relationship).
7. **Image storage:** SP-2 only persists `product_images.asset_id` + sort_order + alt; the `assets` table and pre-signed PUT upload are SP-8. For now, the asset rows are inserted from a dev seed and admin "attach image" endpoints accept an existing `asset_id`. A stub `POST /api/v1/admin/assets/upload-url` returns `{ url: "...", asset_id: "..." }` synthesized from `crypto.randomUUID()` (no real upload), gated behind a `MEDIA_PIPELINE=stub` env flag; SP-8 replaces it.
8. **Migration numbering:** SP-2 takes 0005, 0006, 0007. SP-3 (running in parallel implementation) takes 0008+. If SP-3 lands first numerically, the implementation engineer renames our files to the next available slot before pushing — forward-only ordering preserves history.
9. **Cursor pagination:** opaque cursor is `base64(JSON.stringify({k: <sort_key>, id: <uuid>}))` where `<sort_key>` is the column we sort by (created_at desc by default). Cap 200, default 50.
10. **Faceting:** facet counts computed in the same query as the listing via `GROUPING SETS` / `FILTER (WHERE ...)` aggregates over the active filter set minus the current facet — standard "show count if I add this filter" pattern.

## Execution Notes for the Engineer

- Use the same `withTenant(storeId, async (tx) => …)` helper SP-1 established for every read/write — never bypass.
- Use `migratorDb` only for seeds and migrations; runtime code uses `appDb` via `withTenant`.
- Every admin mutating endpoint MUST require `Idempotency-Key` (use `requireIdempotencyKey` middleware from SP-1's `src/lib/idempotency.ts`).
- All errors via `problem({ type, title, status, detail, errors })` from `src/lib/errors.ts`.
- Cursor pagination only — no `?page=N`. Hard cap 200.
- No `console.log`. Use `logger.{info,debug,warn,error}` from `src/lib/logger.ts`.
- After every drizzle schema change, run `pnpm db:generate` to produce the next migration; commit both the schema file and the generated `.sql` together.
- Hand-written migrations (RLS, search trigger) live alongside drizzle-generated ones; drizzle-kit ignores `.sql` files it didn't produce as long as the meta journal records them — see SP-1's `0004_enable_rls.sql` for the convention.

### Task 7 — Hand-written 0007 search migration

**File:** `src/db/migrations/0007_catalog_search.sql`

```sql
-- Enable extensions
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS unaccent;

-- Add tsvector column
ALTER TABLE products
  ADD COLUMN search_tsv tsvector;

-- Trigger to maintain search_tsv from name, brand, description, attributes
CREATE OR REPLACE FUNCTION products_search_tsv_update() RETURNS trigger AS $$
BEGIN
  NEW.search_tsv :=
    setweight(to_tsvector('simple', unaccent(coalesce(NEW.name, ''))), 'A') ||
    setweight(to_tsvector('simple', unaccent(coalesce(NEW.brand, ''))), 'B') ||
    setweight(to_tsvector('simple', unaccent(coalesce(NEW.description_md, ''))), 'C') ||
    setweight(to_tsvector('simple', unaccent(coalesce(
      (SELECT string_agg(value::text, ' ')
        FROM jsonb_each_text(NEW.attributes)), ''))), 'D');
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER products_search_tsv_trg
  BEFORE INSERT OR UPDATE OF name, brand, description_md, attributes
  ON products
  FOR EACH ROW EXECUTE FUNCTION products_search_tsv_update();

-- Indexes
CREATE INDEX products_search_tsv_gin ON products USING gin (search_tsv);
CREATE INDEX products_name_trgm ON products USING gin (name gin_trgm_ops);

-- Backfill (no-op on greenfield, kept for re-runs)
UPDATE products SET name = name;
```

Also append to `meta/_journal.json` so drizzle-kit recognizes the file (follow the 0004 convention SP-1 established).

**Acceptance:** after migration, inserting a product populates `search_tsv` automatically. `EXPLAIN ANALYZE` on `WHERE search_tsv @@ plainto_tsquery(...)` shows the GIN index in use.

### Task 9 — Cursor pagination helper

**File:** `src/lib/cursor.ts`

```ts
import { z } from 'zod';

export type CursorPayload = { k: string; id: string };

const CursorSchema = z.object({ k: z.string(), id: z.string().uuid() });

export function encodeCursor(p: CursorPayload): string {
  return Buffer.from(JSON.stringify(p), 'utf8').toString('base64url');
}

export function decodeCursor(s: string | undefined): CursorPayload | null {
  if (!s) return null;
  try {
    const decoded = JSON.parse(Buffer.from(s, 'base64url').toString('utf8'));
    return CursorSchema.parse(decoded);
  } catch {
    return null;
  }
}

export function parseLimit(s: string | undefined, def = 50, max = 200): number {
  const n = s ? parseInt(s, 10) : def;
  if (Number.isNaN(n) || n < 1) return def;
  return Math.min(n, max);
}
```

export async function getCategoryTree(storeId: string) {
  return withTenant(storeId, async tx => {
    const rows = await tx.select().from(categories).where(eq(categories.published, true));
    return buildTree(rows);

function buildTree(rows: typeof categories.$inferSelect[]) {
  const byId = new Map(rows.map(r => [r.id, { ...r, children: [] as any[] }]));
  const roots: any[] = [];
  for (const r of byId.values()) {
    if (r.parentId && byId.has(r.parentId)) byId.get(r.parentId)!.children.push(r);

  }
  return roots;

## Risks & Open Questions

1. **trgm index emission by drizzle-kit:** drizzle-kit may or may not emit `gin_trgm_ops` correctly. If it emits but the extension isn't loaded yet, 0005 will fail on a fresh DB. Mitigation: review the generated 0005 and move any trgm index DDL into 0007 manually.
2. **Search ranking tuning:** initial weights (A=name, B=brand, C=desc, D=attrs) are a guess. Will be tuned in SP-7 once content blocks exist. Tracked as open.
3. **Bundle pricing model:** v1 sets bundle price on the bundle variant directly (not computed from components). If the store wants "components × price − discount %", that's a SP-4 promotion concern. Documented here so SP-4 doesn't second-guess.
4. **Soft-delete vs hard-delete:** products use soft delete (deleted_at) to preserve historical order line references. Categories hard-delete (FK to products sets null). Confirm with stakeholder that admins can still see soft-deleted products in an "archive" view (out of scope for SP-2; flagged for SP-6).
5. **i18n on names/descriptions:** v1 stores single-language strings. Multi-locale is a SP-7 concern (content translations table). Out of scope here.
6. **Brand as text vs FK:** v1 stores `products.brand text`. If a `brands` table is later needed (logos, brand pages), data migration is straightforward (`INSERT DISTINCT brand` then ALTER COLUMN). Deferred.
